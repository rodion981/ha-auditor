## Confirmed issues

### Silent truncation of update details

The sensor counted 12 available updates but exposed only ten records in
`available_updates`. `ComponentsAuditor._publish` applies `[:10]` when
publishing this attribute (`__init__.py:1481-1483`), after the complete audit
and assessment are computed. This is a presentation limitation, not evidence
that the two repositories were skipped. README attribute documentation does
not describe this limit, and there is no accompanying truncation indicator.

The omitted details belonged to Entity Availability and Blitzortung Lightning
Card. A separate read-only GitHub-data assessment with the unchanged beta.4
helpers confirmed their complete paths and minor severity:

- Entity Availability `v0.5.7 -> v0.6.0`: two releases, one stable and one
  prerelease; no explicit HA minimum.
- Blitzortung Lightning Card `1.19.0 -> 1.19.1`: one stable release; no explicit
  HA minimum.

Recommended fix: provide access to the full assessed list, or an explicit
bounded list with returned/total counts and a supported way to retrieve the
rest. Increasing an undocumented constant alone does not solve the contract.

### Feature requirement reported as an integration-wide HA minimum

Weather Radar Card `v3.9.0 -> v3.13.0` reported
`minimum_home_assistant_version: 2026.10` and `compatibility_status:
requirement_found`. The extracted source was `v3.11.0-beta1` and concerns the
optional `map_style: MapTiles` feature. That source explicitly disables the
option on older cores and falls back to another style for YAML configurations.
[Stable 3.12.0 notes](https://github.com/jpettitt/weather-radar-card/releases/tag/v3.12.0)
also describe fallback map styles for older cores.

The regex extractor in `release.py:31-42,196-208` recognizes requirement
phrases but does not determine whether they apply to the whole integration or
only a feature. Therefore the extracted number is real, but its global scope
is unsupported. This was reproduced with actual public GitHub release data,
not a synthetic production state.

Recommended fix: distinguish feature-level requirements from an explicit
integration-wide minimum. Keep global compatibility unknown when scope is
unclear and retain the source/context rather than asserting a global minimum.

  says it is a drop-in upgrade from 3.12.0.

  unknown-to-unavailable state change from intermediate release `3.7.1`.
- The ten repository-health findings are separate from available updates;
  twelve active findings do not mean twelve critical updates.

## Evidence limits

This validation does not prove that an update is safe for the owner's specific
dashboard or automations. It performs no real update, new finding resolution,
installed tag-only test, or publication. A green audit is not equivalent to
correct compatibility interpretation; the two issues above remain unfixed.
