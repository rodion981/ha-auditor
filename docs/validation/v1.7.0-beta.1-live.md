# v1.7.0-beta.1 live validation

Date: 2026-10-13. Runtime: Home Assistant Core 2026.9.3.
Release code: `21d332578992507613cc6cd7f3ad1daa779d24fd`.

## Scope and method

The owner-authorized test used a clean HA Auditor installation through HACS,
the Ukrainian Home Assistant interface, and native integration actions.
Five HACS integrations were present. The initial inventory contained no
available HACS updates. No GitHub token or notification action was configured.

Upgrade-path and finding scenarios therefore used temporary Developer Tools
state overrides for the existing HA Auditor update entity. These were fixtures,
not actual installed versions or real pending updates. Release data was fetched
from the public repository. Other repositories were temporarily excluded.

## Confirmed passes

- HACS offered and downloaded the exact `v1.7.0-beta.1` prerelease.
- After the owner restored host/network access, the integration loaded and the
  native Ukrainian setup flow completed successfully.
- Seven integration entities were registered, including the native to-do list
  and finding filter. The integration page reported version `1.7.0-beta.1`.
- The first full audit checked 5/5 repositories, reported `idle`, complete
  inventory coverage, zero errors and zero newly discovered releases.
- Fixture `v1.3.0 -> v1.6.1` produced a complete path with eight release steps,
  seven intermediate releases, individual release links and aggregate signals.
- No explicit minimum HA version was present; compatibility remained `unknown`.
- Checking a to-do item acknowledged it, changed `new: 1` to `acknowledged: 1`,
  and switched attention off. The review state survived an integration reload.
- Unchecking it restored `new: 1` and switched attention on.
- The archived filter hid the update item while preserving the active finding
  count and attention state; the filter was subsequently restored to `all`.
- An action targeting a nonexistent finding returned the Ukrainian error
  "Запитаної знахідки більше немає" without changing finding state.
- An unmatched installed-version fixture returned a `partial` upgrade path.

## Stable blockers reproduced live

### 1. Generic risk vocabulary becomes a breaking-change signal

The v1.4.0 notes describe how critical findings activate. The Ukrainian word
`критичні` matched `критич`, causing a critical classification and a
`breaking_changes` signal despite no declared incompatible change.

Cause: `release.py` reuses all `CRITICAL_TERMS` in `release_signals`, including
generic critical/severity vocabulary. The v1.5.1 wording about clarified token
security similarly became a `security_fixes` signal. Separate explicit change
evidence from generic feature descriptions and security mentions.

Regression fixtures should include the actual bilingual v1.4.0 and v1.5.1 notes,
plus positive explicit breaking-change and vulnerability-fix examples.

### 2. Incomplete upgrade evidence advances finding resolution

After the complete-path finding activated, the installed version was changed
to `qa-unmatched-installed` while the same target remained available.
Two successful audits with `upgrade_path_status: partial` advanced
`clear_confirmations` from zero to one and then two. The existing critical
finding became resolved and attention switched off.

Cause: successful repository fetches are passed to finding reconciliation as
clean checks even when the relevant update path cannot be assessed fully.
An incomplete update assessment must not provide resolution evidence for a
previous update-risk finding. Repository-health checks should remain independent.

### 3. Clearing the exclusions field restores its previous default

Clearing a populated exclusions textarea and submitting showed success, but
reopening the options form revealed the old list. The next audit still excluded
all five repositories. `vol.Optional(..., default=current_value)` restores the
old list when the frontend omits an empty optional field.

Recovery during QA: submit whitespace, which is present in the form payload
and normalizes to an empty exclusion list. The same schema pattern also exists
for the notification action; that field was not populated during this test.

## Evidence limits

- The complete and partial path cases used controlled state overrides.
- No real pending-update path, tag-only repository path, explicit minimum-HA
  example, full host restart persistence, notification delivery, or large
  inventory request-budget test passed in this session.
- The path counted three prereleases alongside five stable releases. Channel
  filtering and the meaning of `versions_behind` need a product decision.
- Local tests and green release-tag CI remain separate evidence from these
  live results. This beta is not ready for promotion to stable.

## Cleanup

The original HACS update state and attributes were restored. The synthetic
finding was removed using the normal exclusion lifecycle; no storage files
were edited. The filter was restored to `all`, notifications stayed disabled,
and no credentials were created or changed.

Two subsequent full ordinary-inventory audits each checked 5/5 repositories
with `status: idle`, `cycle_complete: true`, `excluded_components: 0`, zero
errors, zero available updates and zero newly discovered releases. The active
and resolved finding lists were empty, attention was off, and the to-do count
was zero. The last reported unauthenticated GitHub quota was 34 remaining.

Original settings were restored: no exclusions, daily hour 9, Sunday digest,
request budget 45, no GitHub token and no notification action.
