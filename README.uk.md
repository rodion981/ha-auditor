## Швидке встановлення

1. Відкрийте цей репозиторій у HACS кнопкою нижче та встановіть інтеграцію.
2. Перезапустіть Home Assistant.
3. Натисніть **Add Integration**, щоб запустити налаштування інтеграції.

[![Open in HACS](https://my.home-assistant.io/badges/hacs_repository.svg)](https://my.home-assistant.io/redirect/hacs_repository/?owner=rodion981&repository=ha-auditor&category=integration)

[![Add Integration](https://my.home-assistant.io/badges/config_flow_start.svg)](https://my.home-assistant.io/redirect/config_flow_start/?domain=custom_components_auditor)

> [!NOTE]
> Для кнопки HACS потрібен встановлений HACS. Кнопка Add Integration працюватиме після завантаження кастомної інтеграції та перезапуску Home Assistant.

HA Auditor — це кастомна інтеграція Home Assistant для моніторингу оновлень
інтеграцій, встановлених через HACS. Вона читає примітки до GitHub Releases,
виділяє зміни, на які варто звернути увагу, зберігає важливі знахідки до
підтвердженого вирішення та чітко показує, чи вдалося успішно перевірити всі
репозиторії.

Перед оновленням вона допомагає відповісти на три запитання:

1. Для яких HACS-інтеграцій зараз доступні оновлення?
2. У яких релізах згадуються несумісні зміни, важливі виправлення або нові
   функції?
3. Аудит повний чи частина результату відсутня через помилку GitHub або мережі?

HA Auditor працює лише на читання. Він не встановлює оновлення й не змінює
інші інтеграції.

## Можливості

- Автоматично знаходить активні сутності оновлень HACS-інтеграцій.
- Показує встановлені й доступні версії разом зі стислим описом відповідного
  релізу.
- Класифікує як поточні доступні оновлення, так і нові релізи: критичні,
  важливі, функціональні або незначні.
- Показує ключове слово, через яке реліз отримав свою категорію.
- Зберігає знахідки з часом першого й останнього виявлення, підтвердженнями,
  рекомендацією та історією вирішення.
- Відокремлює проблеми компонентів від помилок GitHub або самого аудиту.
- Під час першого запуску створює тиху базову точку, не видаючи старі релізи за
  нові.
- Розрізняє стани `idle`, `running`, `partial` та `error`.
- Зберігає контрольні точки релізів і чергу тижневого дайджесту після
  перезапусків.
- Підтримує необов'язкові негайні сповіщення та щотижневий дайджест.
- Використовує GitHub ETag, щоб уникати зайвих API-запитів.
- Має українські й англійські екрани налаштування та описи дій.

## Встановлення

### Через HACS як кастомний репозиторій

1. Відкрийте **HACS** у Home Assistant.
2. Відкрийте меню та виберіть **Custom repositories**.
3. Додайте `https://github.com/rodion981/ha-auditor` з категорією
   **Integration**.
4. Відкрийте **HA Auditor** і натисніть **Download**.
5. Перезапустіть Home Assistant.
6. Відкрийте **Налаштування > Пристрої та служби > Додати інтеграцію**.
7. Знайдіть **HA Auditor** і завершіть налаштування.

### Вручну

Скопіюйте каталог `custom_components/custom_components_auditor` до каталогу
`custom_components` у конфігурації Home Assistant, перезапустіть Home Assistant
і додайте **HA Auditor** через **Пристрої та служби**.

## Налаштування

Усі параметри доступні в **Налаштування > Пристрої та служби > HA Auditor >
Налаштувати**.

| Параметр | Призначення |
| --- | --- |
| GitHub-токен | Необов'язковий токен лише для читання. Він збільшує ліміт API та дозволяє повному аудиту перевірити всі знайдені репозиторії за один запуск. |
| Дія сповіщення | Необов'язкова дія Home Assistant, наприклад `notify.mobile_app_your_phone`. Залиште поле порожнім, щоб вимкнути push-сповіщення. |
| Виключені репозиторії | Репозиторії, які не потрібно перевіряти: по одному `owner/repository` у рядку. |
| Година щоденного аудиту | Локальна година Home Assistant, коли починається плановий аудит. Запуск відбувається на 15-й хвилині. |
| День щотижневого дайджесту | День, коли плановий аудит також надсилає накопичений дайджест. |
| Бюджет GitHub-запитів без авторизації | Бюджет API без токена. Метадані, Releases і резервна перевірка Tags можуть потребувати до трьох запитів на репозиторій. |

Збережений токен ніколи не виводиться в атрибутах сенсора. У формі параметрів
залиште поле токена порожнім, щоб зберегти поточний токен, введіть інший для
заміни або увімкніть перемикач видалення, щоб стерти його.

## Запуск аудиту

Планові аудити запускаються автоматично. Для ручного запуску відкрийте пристрій
HA Auditor у **Налаштування > Пристрої та служби** й натисніть
`button.ha_auditor_run_audit`, або додайте цю кнопку на дашборд. Дія
`custom_components_auditor.run_audit` залишається доступною, коли потрібно
вибрати режим або керувати поведінкою сповіщень:

| Режим | Поведінка |
| --- | --- |
| `daily` | Перевіряє наступну налаштовану порцію репозиторіїв. |
| `full` | Перевіряє всі репозиторії за наявності токена; без токена перевіряє одну порцію. |
| `digest` | Перевіряє репозиторії та надсилає накопичений тижневий дайджест. |

Приклад виклику дії:

```yaml
action: custom_components_auditor.run_audit
data:
  mode: full
  notify: false
```

Встановіть `notify: false`, якщо потрібно оновити сенсор без негайних
сповіщень.

## Керування знахідками

Кожна активна знахідка має стабільний `finding_id`. Використовуйте його з
нативними діями HA Auditor через **Інструменти розробника > Дії** або в
автоматизації:

```yaml
action: custom_components_auditor.acknowledge_finding
data:
  finding_id: "ad-ha/kidschores-ha:health"
```

- `acknowledge_finding` залишає знахідку видимою, але позначає її переглянутою.
- `snooze_finding` прибирає її з індикатора уваги на 7 або 30 днів; додайте
  `days: 7` або `days: 30` до даних дії.
- `ignore_finding` приховує саме цю знахідку з індикатора уваги до зміни
  доступної версії або стану репозиторію.
- `restore_finding` повертає підтверджену, відкладену або проігноровану знахідку
  до стану `new`.

Технічно знахідка залишається активною, доки аудитор не підтвердить зникнення
її причини. Нова версія оновлення отримує новий fingerprint і автоматично
повертається до `new`, навіть якщо попередню версію вже переглянуто.

## Сутності

Інтеграція створює п'ять нативних сутностей Home Assistant:

| Сутність | Призначення |
| --- | --- |
| `sensor.custom_components_auditor` | Кількість релізів, уперше побачених під час останнього аудиту; повний результат міститься в атрибутах. |
| `sensor.ha_auditor_active_findings` | Кількість постійних важливих знахідок; їхній життєвий цикл, рекомендація та URL містяться в атрибутах. |
| `binary_sensor.ha_auditor_attention_required` | Вмикається лише тоді, коли є хоча б одна нова непереглянута активна знахідка. |
| `binary_sensor.ha_auditor_audit_problem` | Вмикається, коли останній аудит частковий або завершився помилкою. |
| `button.ha_auditor_run_audit` | Запускає найповніший аудит, дозволений поточними GitHub-обліковими даними, без push-сповіщення. |

| Атрибут | Значення |
| --- | --- |
| `status` | Поточний стан: `idle`, `running`, `partial` або `error`. |
| `last_attempt` | Час початку останнього аудиту. |
| `last_successful_audit` | Час останнього повністю успішного аудиту. |
| `total_components` | Кількість знайдених HACS-інтеграцій. |
| `targeted_this_run` | Репозиторії, вибрані для останнього запуску. |
| `checked_this_run` | Репозиторії, які вдалося перевірити. |
| `deferred_components` | Репозиторії, відкладені до наступних запусків, коли поточна порція без авторизації менша за весь знайдений список. |
| `cycle_complete` | `true`, якщо останній запуск успішно перевірив увесь знайдений список. |
| `updates_available` | Кількість оновлень, які зараз пропонує HACS. |
| `available_updates` | Встановлена й нова версії, рівень уваги, причина, стислий опис, URL та статус приміток до релізу: `found`, `not_found` або `not_checked`. |
| `available_update_counts` | Поточні оновлення за категоріями `critical`, `important`, `feature`, `minor` або `unknown`. |
| `repository_health_counts` | Кількість архівованих репозиторіїв і репозиторіїв без push щонайменше 730 днів. |
| `repository_health_details` | Статус репозиторію, дата останнього push, дні без активності та URL GitHub. |
| `excluded_repositories` | Репозиторії, пропущені через параметри інтеграції. |
| `attention_required` | Чи потребує поточний результат уваги користувача. |
| `audit_problem` | Чи був останній аудит частковим або невдалим. |
| `active_finding_count` | Кількість активних важливих знахідок. |
| `active_findings` | Стабільний ID, репозиторій, компонент, тип, важливість, стан перегляду, часові поля, рекомендація та URL кожної активної знахідки. |
| `finding_counts` | Активні знахідки за важливістю, джерелом і станом `new`, `acknowledged`, `snoozed` або `ignored`. |
| `findings_pending_confirmation` | Можливо неактивні репозиторії, які очікують повторного успішного підтвердження. |
| `pending_findings` | Деталі кандидатів про неактивні репозиторії, що очікують підтвердження. |
| `recently_resolved_findings` | Знахідки, відсутність яких підтверджено двома чистими перевірками; зберігаються 30 днів. |
| `finding_changes` | Знахідки, активовані або вирішені під час останнього запуску. |
| `critical`, `important`, `new_features`, `minor` | Нові релізи за категоріями. |
| `last_run_changes` | Релізи, знайдені під час останнього запуску. |
| `pending_digest_changes` | Релізи, що чекають щотижневого дайджесту. |
| `error_details` | Невдалі перевірки, згруповані за типом помилки. |
| `github_token_configured` | Чи налаштовано GitHub-токен. |
| `github_authenticated` | Чи прийняв GitHub налаштований токен під час останнього запуску. |
| `github_rate_remaining` | Залишок квоти GitHub API, якщо він доступний. |

Докладні атрибути життєвого циклу знахідок містяться в
`sensor.ha_auditor_active_findings`; початковий сенсор результату зберігає
стислі лічильники для наявних дашбордів і автоматизацій.

Статус `partial` означає, що хоча б один вибраний репозиторій не перевірено
через помилку або перервану послідовність запитів. Успішна порція без токена
залишається у стані `idle`; атрибути `deferred_components` і `cycle_complete`
показують, чи охопив запуск увесь знайдений список.

Готова стандартна картка доступна у
[`examples/dashboard.yaml`](examples/dashboard.yaml).

## Як це працює

Під час першого успішного запуску HA Auditor одразу оцінює кожне доступне
HACS-оновлення, для якого знайдено відповідний GitHub Release. Водночас він
зберігає останній відомий реліз кожного репозиторію без створення старих
сповіщень. Наступні запуски порівнюють GitHub Releases із цією базовою точкою,
зберігають нові знахідки й оновлюють сутності. Контрольні точки та
невідправлені записи дайджесту зберігаються у сховищі Home Assistant.

Доступні оновлення HACS і нові GitHub Releases навмисно показуються окремо.
Для інтеграції може бути доступне оновлення, навіть якщо цей реліз не є новим
для аудитора.

Якщо репозиторій не має GitHub Releases, HA Auditor переходить до останніх
GitHub Tags. Знайдений тег позначається як джерело без вигаданих приміток до
релізу чи оцінки ризику. Метадані репозиторію також перевіряються на прапорець
GitHub `archived` і відсутність push щонайменше 730 днів.

Знахідки про критичні й важливі оновлення та архівовані репозиторії
активуються одразу. Неактивність репозиторію має бути зафіксована двома
успішними перевірками. Для вирішення активної знахідки також потрібні дві чисті
перевірки. Репозиторій, відкладений через бюджет API або пропущений через
помилку GitHub, не змінює стан знахідки. Вирішені знахідки зберігаються 30 днів,
а знахідки виключених або видалених репозиторіїв видаляються зі сховища.

Підтвердження, відкладення чи ігнорування змінює лише стан перегляду. Знахідка
залишається в `active_findings`, але індикатор уваги вмикають лише знахідки зі
станом `new`. Відкладені знахідки автоматично відкриваються після завершення
заданого строку.

Якщо GitHub відхиляє налаштований токен, HA Auditor створює виправну проблему в
Home Assistant Repairs. Майстер може перевірити й зберегти новий токен або
видалити відхилений токен і продовжити роботу порціями без авторизації.

## Обмеження

- Класифікація є детермінованою підказкою за ключовими словами, а не аудитом
  безпеки чи доказом несумісності.
- Перед встановленням критичного або важливого оновлення завжди відкривайте
  повні примітки до релізу.
- Репозиторії лише з тегами можна відстежувати, але тег не містить приміток до
  релізу й не дає достатньо даних для оцінки ризику.
- Без токена HA Auditor шукає точну версію HACS серед максимум 100 GitHub
  Releases і 100 Tags. Із токеном він перевіряє до трьох сторінок кожного
  джерела та зупиняється одразу після збігу. Якщо збігу все одно немає,
  оновлення позначається як `unknown` без вигаданої оцінки.
- Ліміт GitHub API без авторизації нижчий, тому для великих інсталяцій варто
  використовувати токен лише для читання або обробляти репозиторії порціями.

## Приватність і безпека

HA Auditor працює всередині Home Assistant і звертається до GitHub API по
публічні метадані репозиторіїв, Releases і Tags. Він не встановлює оновлення,
не змінює інші інтеграції й не показує збережений токен у сенсорі. Сповіщення
надсилаються лише через явно налаштовану користувачем дію Home Assistant.

Докладні атрибути сутностей залишаються доступними для дашбордів, шаблонів і
автоматизацій, але HA Auditor виключає їх з історії Recorder, щоб не зберігати
великі результати аудиту повторно. **Завантажити діагностику** показує лише
ознаки конфігурації, перебіг роботи та зведені лічильники; GitHub-токен, ціль
сповіщень і назви репозиторіїв до неї не потрапляють.

Не додавайте до публічних Issues токени, конфігурацію Home Assistant, дані
`.storage` або вміст сповіщень. Докладніше у [`SECURITY.md`](SECURITY.md).

## Розробка

```bash
python -m pip install -r requirements_test.txt
python -m compileall -q custom_components
ruff check custom_components tests
python -m pytest
```

Runtime-тести Home Assistant потребують Linux або WSL, Python 3.14 й окремого
середовища, оскільки сам Home Assistant не підтримує нативний Windows runtime:

```bash
python -m pip install -r requirements_runtime_test.txt
python -m pytest tests/test_runtime.py
```

Автоматизовані тести перевіряють класифікацію релізів, заперечення фраз про
несумісні зміни, очищення описів, дедуплікацію, роботу конфігурації, переклади,
метадані репозиторію, життєвий цикл знахідок і базовий пошук секретів.
Runtime-перевірка додатково завантажує інтеграцію через Home Assistant,
реєструє її сутності й дії, перевіряє збереження стану знахідки після
перезавантаження config entry та відсутність приватних значень у діагностиці.

Хочете додати іншу мову інтерфейсу? Дивіться
[`CONTRIBUTING.md`](CONTRIBUTING.md#adding-a-translation). Кожна локаль
зберігається окремим JSON-файлом у папці `translations`, тому змінювати
Python-код не потрібно.
